WorkshopKill It and Watch It Come Back: Hands-on with Reliaburger

Reliaburger
I have never run a Kubernetes cluster. Yes, I said it. Are you still with me? Cool! Over the past last five years I talked to thousands of SREs and platform engineers at the conferences I run with my team: SREday, LLMday, PLATFORMday and Conf42. The same story keeps coming back. Before the first container hits production you step into the world of Kubernetes, and then you need to build a whole team just to keep it running. A killjoy for many smaller teams. We started talking with my brother, Miko Pawlikowski, how we could help the community ease some of these pains. Miko has been running platform teams on Kubernetes for 10+ years, leading him to start writing Reliaburger: one Rust binary with the scheduler, gossip, Raft, eBPF service discovery, ingress, mTLS, registry, metrics, logs, GitOps and chaos testing inside, driven by TOML. An app with health checks, ingress and autoscaling is twelve lines. He wrote the software. I am here to hand it to the community and see what you do with it. This is a hands-on session, so bring a laptop (macOS on Apple silicon or Linux; Windows is not supported yet). In 30 minutes you will: 1. Install Reliaburger with one command and start a node on your laptop. No container runtime, no root, no VMs: the built-in process runtime runs plain binaries. 2. Deploy an app from a twelve-line TOML file and watch it in the terminal dashboard and the web UI. 3. Ship a deliberately sick version and watch the health checker restart it, then roll back with one command. 4. Break it on purpose with the built-in fault injector: kill an instance, freeze another, and let relish wtf explain what just happened. 5. Read the manual and the source code from inside the binary, so you can keep going after the session. 6. Tell us what broke and what you liked. Reliaburger is free and open source (Apache 2.0), and it is version 0.1, so it will break. That is where you come in. We are looking for helpers, burger ambassadors and contributors: people who will run it, break it, file the issues, write the docs and tell their teams. There are millions of practitioners running parts of Kubernetes they do not need, with more people than they should need to run it. We want this to become a community-driven project, just as our conferences are.... Read more

Felipe Sanz

The Exam Moved to Monday: Agent Memory That Knows What to Forget

New Premise
Most agent memory starts as an append-only log: embed what the user said, store it, retrieve the nearest matches later. Then a student tells their AI tutor the midterm is Thursday, and a week later says it moved to Monday. Both facts are now in the vector store, and similarity search has no way to know the second cancels the first. This talk walks through the long-term memory I designed and built for an AI tutor used by university students. Every extracted fact ends in one of four operations: add, update, delete, or ignore. Vector similarity only finds the closest existing memory. A small LLM picks the operation, because embeddings show that two sentences concern the same exam and say nothing about which is still true. I'll cover the rest of the pipeline too: a cheap router that skips the nine turns in ten with nothing worth remembering, six education-specific memory categories, twenty recalled candidates reranked to five, and a chat that keeps answering when memory fails. I'll also cover the failure modes this design brings, including two data stores written without a transaction and background writes that a deploy can drop. You'll leave with the four-operation merge loop and a checklist of failure modes for your own memory layer.... Read more

Timothy Porter

Zero-Waste Compute: Turning Idle Workstations into a Private AI Cluster

Mod Tech Labs
Most studios and engineering teams own a fleet of powerful GPU workstations that sit idle every night and weekend, then rent cloud GPUs for their AI pipelines. At MOD we are building NOAH, a coming feature that quietly harvests that idle capacity: - it runs AI jobs on a desk machine while nobody is using it; - it steps aside the moment its owner comes back; - it keeps every job and every byte of data inside the company's own walls. This talk shares what we have learned so far: - Defining "idle" was hard. Our first version mistook our own background services for a user's workload, so it never harvested anything. - The owner must always win. Jobs pause first, then are evicted and requeued. Courtesy evictions must never count as job failures. - One unreachable server must not trigger a fleet-wide shutdown. We learned this when a routine restart made every machine stop its own models. - Windows needs a lighter runtime. Docker Desktop is too heavy to leave running on an artist's machine, so we are building on Microsoft's new WSL containers, which became generally available this fall. They start only when a job runs and disappear when it's done. You'll leave with a practical checklist for harvesting idle compute safely: presence detection, preemption, scheduling, network lockdown and proving where your data went.... Read more

Raul Leite

vLLM Explained: What an Open Source Inference Server Actually Does

Red Hat
Running a model on your laptop is easy (depending on your machine, of course). Serving it to hundreds of users at once, on expensive GPUs, is a different problem. That's the job of an inference server, and it's quickly becoming a core piece of every platform. In this session, we'll open up vLLM, one of the most widely used open source inference servers, at the architecture level. No code, no vendor pitch. We'll cover what an inference server does between your application and the GPU, and the two ideas that make vLLM fast: continuous batching, which keeps the GPU busy across many users, and PagedAttention, which manages GPU memory the way an operating system manages pages. Then we'll zoom out: where vLLM fits in your architecture, how its OpenAI-compatible API makes it a drop-in backend, how projects like KServe and llm-d scale it on Kubernetes, and when a lighter option like llama.cpp is the better choice. Key takeaways: What an inference server is and why platform teams now own it The two core ideas behind vLLM's performance, explained simply A reference architecture for serving open models on Kubernetes... Nelma Perera

Trusting Hundreds of Agents in Production

Egen
Multi agent systems are easy to demo and hard to operate, and the hard part grows with the agent count. With a few agents you can read the logs by hand. With hundreds of them, orchestrators and specialized sub agents handling real work for a large enterprise, the questions change: which agent made this call, why did this run take four times longer than yesterday, what does healthy look like across the whole fleet, and who gets paged. In this talk I will walk through what I have learned building and running systems of hundreds of agents on Google Cloud for enterprise clients, from the platform side. We will cover tracing every run as a tree of agent, tool and model calls, defining metrics and SLOs that describe agent and model performance rather than just uptime, catching loops and runaway cost early, the troubleshooting patterns that shorten incidents, and where evals fit: scoring sampled production runs with a model as judge and turning the failures into test cases. You will leave with a short list of what a developer platform needs to provide before hundreds of agents can be trusted in production.... Read more

Kishore Pulagam

The Second Tenant Problem: When an AI Pipeline Becomes a Platform

PayPal
Platform engineering spent a decade learning to share infrastructure between teams. AI platforms break that model, because the tenants are now agents and model-driven workloads that generate their own load, consume every token they are given, act with delegated authority, and change behavior whenever the model beneath them changes. This talk lays out the control plane I have built for that world, running classical ML, open-weight models, and frontier APIs behind one contract in a regulated enterprise. I will walk through how workloads are placed across models and trust zones, modeled as a filter-score-bind scheduling cycle: data classification and jurisdiction are hard constraints, and capability, latency, and cost are scored. I will then cover how capacity is shared, with per-tenant GPU and task isolation, token budgets, admission control, and fallback paths when GPUs saturate. Advanced topics include scoping agent authority at the tool layer with MCP, prompt isolation and injection guardrails across text and image payloads, and per-workload regression gates for model upgrades. The result is a platform where model capability is allocated deliberately, every agent runs inside a boundary the platform enforces, and replacing a model becomes a routine deployment.... Read more
