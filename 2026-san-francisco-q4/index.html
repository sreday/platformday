Felipe Sanz

New Premise
The Exam Moved to Monday: Agent Memory That Knows What to Forget
Abstract

Most agent memory starts as an append-only log: embed what the user said, store it, retrieve the nearest matches later. Then a student tells their AI tutor the midterm is Thursday, and a week later says it moved to Monday. Both facts are now in the vector store, and similarity search has no way to know the second cancels the first. This talk walks through the long-term memory I designed and built for an AI tutor used by university students. Every extracted fact ends in one of four operations: add, update, delete, or ignore. Vector similarity only finds the closest existing memory. A small LLM picks the operation, because embeddings show that two sentences concern the same exam and say nothing about which is still true. I'll cover the rest of the pipeline too: a cheap router that skips the nine turns in ten with nothing worth remembering, six education-specific memory categories, twenty recalled candidates reranked to five, and a chat that keeps answering when memory fails. I'll also cover the failure modes this design brings, including two data stores written without a transaction and background writes that a deploy can drop. You'll leave with the four-operation merge loop and a checklist of failure modes for your own memory layer.

Bio

Felipe Sanz is the founder of New Premise, an Austin consultancy that helps companies put AI to work one department at a time and measures the result in return on investment. Before New Premise, he designed and built the long-term memory system and the evaluation process for an AI tutor used by university students, following three and a half years at Celonis building machine learning for the global go-to-market organization. Felipe has also volunteered with Austin AI Hub, building AI tools for nonprofits that fight human trafficking, and guest lectured on advanced databases at IE University. He writes about AI at felipe-sanz.com.

Byron Ellis

Faros
Preventing a Software Dark Age
Abstract

As organizations adopt agentic engineering, planning, iteration, and PR reviews are all occurring via agents without much in the way of visibility. Architectural decisions and design context are moving transient AI session transcripts rather than durable engineering artifacts that have been the foundation of developing reliable software. It’s not that the work of design and review isn’t happening, it’s that we’re in a dark age where the record of it is deleted due to a 30 day retention policy because unlike traditional SDLC artifacts we can’t be sure it doesn’t contain sensitive data. In this talk we’ll cover some ideas on how we as an industry can start to dig into this session data not only to understand ROI but also perhaps to generate new durable artifacts that actually let us produce more reliable software than we could before.

Bio

Byron recently joined Faros.ai with the suitably ambiguous title “Member of Technical Staff” to build tools that help organizations fully adopt agentic development practices after going through the process first hand. He came to Faros.ai from Linked in where he was a Principal Staff Engineer at LinkedIn where he focused on large scale Data Infrastructure projects. Prior to that he spent time in Google Cloud on the BigQuery and Dataflow teams as well as YouTube where he spent several years working on Trust and Safety infrastructure.

Mark Pawlikowski

Reliaburger
WorkshopKill It and Watch It Come Back: Hands-on with Reliaburger
Abstract

I have never run a Kubernetes cluster. Yes, I said it. Are you still with me? Cool! Over the past last five years I talked to thousands of SREs and platform engineers at the conferences I run with my team: SREday, LLMday, PLATFORMday and Conf42. The same story keeps coming back. Before the first container hits production you step into the world of Kubernetes, and then you need to build a whole team just to keep it running. A killjoy for many smaller teams. We started talking with my brother, Miko Pawlikowski, how we could help the community ease some of these pains. Miko has been running platform teams on Kubernetes for 10+ years, leading him to start writing Reliaburger: one Rust binary with the scheduler, gossip, Raft, eBPF service discovery, ingress, mTLS, registry, metrics, logs, GitOps and chaos testing inside, driven by TOML. An app with health checks, ingress and autoscaling is twelve lines. He wrote the software. I am here to hand it to the community and see what you do with it. This is a hands-on session, so bring a laptop (macOS on Apple silicon or Linux; Windows is not supported yet). In 30 minutes you will:

  1. Install Reliaburger with one command and start a node on your laptop. No container runtime, no root, no VMs: the built-in process runtime runs plain binaries.
  2. Deploy an app from a twelve-line TOML file and watch it in the terminal dashboard and the web UI.
  3. Ship a deliberately sick version and watch the health checker restart it, then roll back with one command.
  4. Break it on purpose with the built-in fault injector: kill an instance, freeze another, and let relish wtf explain what just happened.
  5. Read the manual and the source code from inside the binary, so you can keep going after the session.
  6. Tell us what broke and what you liked. Reliaburger is free and open source (Apache 2.0), and it is version 0.1, so it will break. That is where you come in. We are looking for helpers, burger ambassadors and contributors: people who will run it, break it, file the issues, write the docs and tell their teams. There are millions of practitioners running parts of Kubernetes they do not need, with more people than they should need to run it. We want this to become a community-driven project, just as our conferences are.

Bio

Mark Pawlikowski runs SREday, LLMday and PLATFORMday, in-person conferences for the people who keep production up, and Conf42 online. He is not an engineer. He has spent the last five years listening to SREs and platform engineers describe what their work is actually like, and now brings Reliaburger, his brother Miko's batteries-included container orchestrator, to that community to play with, break and build on.

Prasad M K

Wipro
Your Logs Vanished and Nothing Errored: Three Ways Kubernetes Drops Logs Silently
Abstract

Kubernetes loses container logs in three ways that never reach the application: kubelet rotation lag under heavy writes, disk-pressure eviction that deletes a pod's log directory, and a race between rotation and the log shipper's read cycle. Each one is documented in Kubernetes and Fluent Bit issue trackers (#110630, #134324, #10414), but nobody ties them together. I'll show how application-level sequence markers make these gaps visible, and how to classify each gap by cause using kubelet events and node conditions. Attendees leave with the settings to tune and a simple way to detect loss in their own pipelines.

Bio

Prasad M.K. is a Cloud Solution Architect and Full Stack SRE with 25+ years of experience engineering high-availability systems for Fortune 500 accounts. He specializes in Kubernetes, large-scale data pipelines (Kafka/Pulsar), and agentic AI architectures on AWS Bedrock. Prasad is the author of DAY ONE AI and regularly publishes research on AI agent governance and system design.

Sergey Sergeev

Splunk (Cisco)
From Agent Chaos to Voice-Driven Flow: Building a Self-Improving Knowledge Management Suite
Abstract

A year ago my “AI-assisted” workflow was still manual: open five coding agents, chase which session owned which task, paste context by hand, and discover merge conflicts only when something already hurt. The agents were smart; the system was not. I kept losing the plot between ideation, implementation, and “wait, who has the worktree?” So I built the coordination layer I wished existed—and then I made the suite run itself. What started as a personal knowledge board became a voice-driven dashboard with automated implementers that claim work, track sessions, and keep a living queue. Auto-ideation surfaces the next cuts. A “merge doctor” watches for conflict and repair cases instead of letting mid-merge worktrees become archaeology. When an implementation stack needs a human, it doesn’t wait for me to refresh a browser—it reaches me on the voice terminal I’m already using. The interesting part isn’t any single feature. It’s the before/after: from fragmented agent babysitting to a self-optimizing loop where every painful failure—stale pulls, stuck claims, silent merge flakes—becomes a product requirement the next day. The tool improves the workflow; the workflow feeds the tool. In twenty-five minutes I’ll walk the architecture as lived experience: what broke, what we automated, where humans still belong, and what I’d change if I were demoing this to strangers instead of myself. Bring scars and opinions—I want both.

Bio

Sergey Sergeev is a Senior Staff Engineering Architect for Observability for AI at Splunk (Cisco). He took AI Agent Monitoring from hackathon demo to GA, contributes to the OpenTelemetry GenAI Semantic Conventions SIG, and designs production instrumentation and evaluation systems for agentic workloads. He holds two US patents and has 20+ years building high-scale distributed data systems.

Manu Gurudatha

PagerDuty
Hurdles for Adoption of AI Across Incident Management
Abstract

Everyone building AI into incident management assumes the hard part is the model and accuracy: better anomaly detection, smarter correlation, more reliable auto-remediation. Having spent years watching how teams actually adopt (or stall on) this technology, including our own at PagerDuty, I've found the technology is rarely the blocker. This talk looks at the real, recurring patterns that stall AI adoption in incident response: getting customers to start using it long enough for a positive reinforcing loop to take hold, organizations bolting AI onto a process that was never consistent enough to automate in the first place, cost overruns that erode trust in the ROI, and the harder problem of telling AI-created incidents apart from human-created ones. Even with high-quality signals and a clear value proposition, these remain the true blockers to adoption. This isn't a technical deep dive, it's a product and organizational lens on a problem I'm actively working through: what separates teams that successfully bring AI into their incident workflow from teams that stall out after the pilot. Expect real patterns, some surprising ones, and an honest look at what's still unsolved.

Bio

Manu Gurudatha is a VP of Engineering at PagerDuty, where he drives the Incident Management, AIOps, CSOps, Status Pages that power PagerDuty's end-to-end customer journeys. Prior to PagerDuty, Manu led Engineering organizations in several companies, ranging from Series A startups to giants like Salesforce, where he led engineering for their Health Cloud unit. With his previous experiences, Manu has a proven track record of building strong products and platforms, sometimes from scratch and scaling those to sustain performance for thousands of customers.

Roy Derks

IBM
Agent Sandboxes Are the Missing Runtime for AI
Abstract

AI agents are no longer just calling APIs. They're writing code, executing commands, browsing the web, and interacting with entire systems. But giving agents more autonomy also introduces new risks. How do you let an agent execute arbitrary code without exposing your infrastructure, credentials, or sensitive data? That's where agent sandboxes come in. In this talk, we'll explore why isolated execution environments are becoming a critical part of the agentic AI stack, how technologies like containers and microVMs enable secure execution, and how to architect agents that can safely run code, use tools, and interact with real-world systems.

Bio

Arunkumar Mathiyazhagan

Amazon
Ghost APIs — Why Your Deprecated Endpoints Are an Attacker's Best Friend
Abstract

Every API team deprecates endpoints, but almost none fully kill the traffic. Across complex distributed systems, deprecated endpoints frequently remain reachable long after documentation is removed—creating a sprawling, invisible attack surface hiding in plain sight. We call these Ghost APIs. In this session, I will walk through how to identify, measure, and systematically eliminate that attack surface—developing a security pattern that establishes a secure-by-default reference standard across distributed services. Attendees will learn:

  • How Ghost APIs form and why they persist even in mature, well-governed API platforms.
  • A practical playbook for API deprecation that combines continuous traffic analytics, client outreach, and secure-by-default interceptors.
  • How to build deprecation hygiene into your CI/CD pipeline so Ghost APIs never accumulate again.

Senior Software Engineer at AWS Athena with 16+ years of experience leading teams and architecting hyperscaler-scale distributed systems serving 30k TPS across 35 AWS regions. Deep technical expertise in low-level memory and IO optimization, serverless compute platforms (Firecracker microVMs), and Java/Python/Go/Rust distributed microservices. Recognized for delivering re:Invent launches end-to-end.

Hariharan Subramanian

Microsoft
Beyond the Sunset: Real-World Lessons Migrating from Ingress-NGINX to Kubernetes Gateway API at Scale
Abstract

Migrating production edge traffic from legacy Ingress controllers (like ingress-nginx) to Envoy-based implementations of the Kubernetes Gateway API is rarely as simple as running an automated manifest converter. The real challenge lies in bridging subtle behavioral gaps—unsupported annotation hacks, different timeout models, and altered connection-pooling semantics—without causing downtime or localized outages. This talk shares production-tested patterns for orchestrating a zero-downtime, safe migration across multi-cluster environments using an external, health-driven traffic steering strategy. Attendees will learn: Dual-Plane Traffic Steering & Dynamic Probing: How to decouple legacy and modern ingress planes behind weighted external DNS and global traffic directors, turning migration into an incremental canary rather than a high-risk cutover. Telemetry-Driven Health Probing: Why standard endpoint liveness checks fail during ingress migrations, and how to wire synthetic health-probe endpoints directly to proxy-level downstream metrics (e.g., Envoy /stats downstream connection and handshake error thresholds) to automatically gate traffic based on true downstream health. Quorum-Based Automatic Rollbacks: How to implement a fleet quorum threshold across ingress proxy replicas—automatically flipping the global canary back to the legacy plane the moment partial replica failure occurs, preventing zombie instances from serving errors. The DNS Caching Dilemma: The operational reality of DNS-based routing: handling aggressive client-side caching, calculating cost/query load trade-offs when temporarily dropping TTLs (e.g., from 300s to 30s), and safely stepping TTLs back up once cutover stabilizes. The "Broken Annotations" Trap: Practical strategies for mapping bespoke NGINX annotations, snippet rewrites, and authentication hooks into native Gateway API resources and extension filters.

Bio

Hariharan Subramanian is a Senior Software Engineer at Microsoft working on Azure Kubernetes Service (AKS), specializing in large-scale cloud infrastructure, scalability, and secure distributed systems. With over 16 years of industry experience across health, retail, and cloud infrastructure, he brings deep, hands-on production expertise to complex platform transitions. Hariharan is an active contributor and reviewer for the open-source Envoy Gateway project, focusing on modern ingress architectures, Kubernetes Gateway API adoption, and secure service-to-service communication with Istio.
